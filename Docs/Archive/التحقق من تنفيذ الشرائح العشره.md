### Slice 4 — Item uniqueness + incremental item CRUD — Implemented with Deviations

**Evidence:**
- Application: `Features/PriceLists/Commands/{AddPriceListItem,UpdatePriceListItem,DeletePriceListItem}/*.cs`
- EF config: `Infrastructure/Persistence/Configurations/Settings/PriceListItemConfiguration.cs`
- Migrations: `20260820120000_Slice4PriceListItemUniquenessAndForeignKeys.cs` + `20260820142710_Phase1C_FixPriceListItemUniqueIndexFilter.cs`
- Tests: `AddPriceListItemCommandHandlerTests.cs`, `UpdatePriceListItemCommandHandlerTests.cs`, `DeletePriceListItemCommandHandlerTests.cs`, `PriceListItemUniqueIndexIntegrationTests.cs`

**Deviations found:**

1. **Missing explicit FK on `PriceListItems.PriceListId` in the migration Up():** Plan requires FKs `FK_PriceListItems_PriceLists_PriceListId` (cascade) AND `FK_PriceListItems_Tests_TestId` (restrict). The migration only emits `AddForeignKey` for the Tests FK. The PriceList FK is present in the EF `Configuration` and in the model snapshot but was never a discrete migration step (implying it must have existed since `InitialCreate`). Still a documentation-vs-migration discrepancy.

2. **`UpdatePriceListItemCommandHandler` and `DeletePriceListItemCommandHandler` do not touch the parent `PriceList` at all.** The plan is silent on this specifically, but this means changing a single item's price never bumps the parent list's `UpdatedAt`. Consistent with the "wholesale replace" legacy handler, so not a hard defect but a soft one for audit lineage.

3. **Filter fix through a second migration (`Phase1C_FixPriceListItemUniqueIndexFilter`):** The first migration (`Slice4…`) created the unique index WITHOUT the `[IsDeleted] = 0` filter, then a corrective follow-up migration dropped and re-created it with the filter. This is *schema drift*: the plan promised a single migration `20260821_Module11_S4_PriceListItemUniqueAndFks.cs` with the filter from the start. The end-state is correct on a fresh DB, but any deployment that ran the intermediate state would have blocked legitimate soft-delete-then-reinsert flows.

4. **`AddPriceListItem` uniqueness pre-check** uses `IPriceListItemRepository.GetByPriceListAndTestAsync(...)` which does NOT filter by `IsDeleted` (it queries `_context.PriceListItems.AsNoTracking().FirstOrDefaultAsync(i => i.PriceListId == priceListId && i.TestId == testId, ct)`). The global soft-delete query filter on `PriceListItem` (if any is configured) hides deleted rows, so this is *probably* OK — but the code is fragile. The integration test `PriceListItemUniqueIndexIntegrationTests` only proves the DB-level index, not that the application-layer pre-check honours soft-delete.

**Test coverage:** OK for happy paths but does NOT include the plan's mandated "OQ-2 test — editing item in list A doesn't affect list B via repository verify" — `UpdatePriceListItemCommandHandlerTests` only asserts `item.Price == 25m` and does not construct a second list.

### Slice 5 — Custom Groups schema uplift — Implemented with Deviations

**Evidence:**
- Domain: `Domain/Entities/Core/TestGroup.cs` — `GroupPrice` property removed; `[NotMapped] TotalGroupPrice` present. `Domain/Entities/Core/TestGroupItem.cs` — `Price` field added, `DisplayOrder` retained.
- EF: `Configurations/Core/TestGroupConfiguration.cs` — no `GroupPrice` reference remains; no `Ignore(e => e.TotalGroupPrice)` (not needed at run time because it is `[NotMapped]`, so functionally equivalent). `Configurations/Core/TestGroupItemConfiguration.cs` — `Price decimal(18,2) IsRequired`, filtered unique index, FK to `TestGroups` (cascade), FK to `Tests` (restrict).
- Migration: `20260820094142_Slice5CustomGroupsSchemaUplift.cs`.

3. No `Ignore(e => e.TotalGroupPrice)` in `TestGroupConfiguration.cs`. In EF Core 8 an unreadable auto-property is not mapped without a setter, and the `[NotMapped]` attribute on the entity is honoured, so functionally correct — but the plan explicitly asked for the `Ignore` call.

**Test coverage:** the three domain-invariant asserts (`TotalGroupPrice_SumsNonDeletedItemPrices`, `TotalGroupPrice_ReturnsZeroForEmptyGroup`, `TestGroupItem_Price_DefaultsToZero`) match the plan. No `CustomGroupSchemaUpliftMigrationTests.cs` exists — the plan asked for a test that queries `sys.indexes.filter_definition` — not implemented.

### Slice 6 — Custom Groups per-action triads + queries + `ITestGroupRepository` — Implemented with Deviations

**Evidence:** every promised feature folder exists under `Features/TestGroups/Commands/{AddTestGroup,RenameTestGroup,DeleteTestGroup,AddTestToGroup,UpdateTestInGroup,RemoveTestFromGroup}/` and `Features/TestGroups/Queries/{GetTestGroups,GetTestGroupById}/`. The `ITestGroupRepository` interface with `GetByIdWithItemsAsync`, `GetAllWithItemsAsync`, `NameExistsAsync` is present, implemented in `TestGroupRepository`, and registered in `DependencyInjection.cs`. Extensive unit tests exist in `TestGroupCommandHandlerTests.cs`, `TestGroupQueryHandlerTests.cs`, `TestGroupValidatorTests.cs`.

**Deviations:**

1. **No `TestGroupMappingProfile.cs` was created**, contrary to the explicit plan requirement. All DTO population is hand-rolled inside `GetTestGroupsQueryHandler` and `GetTestGroupByIdQueryHandler` (no AutoMapper). Functional but deviates from the plan and from the convention Slice 1 established for `PriceListMappingProfile`.

2. **`DeleteTestGroupCommandHandler` injects `ITestGroupItemRepository`**, so the OQ-7 structural claim that "the handler's dependency set does NOT include any visit-side collaborator" holds only for visits — but the *plan* wanted the item cascade to happen through the `TestGroup` aggregate, not through a second repository. Runtime behaviour is fine (both group and items get `IsDeleted = true`); the ctor contract deviates.

3. **`RemoveTestFromGroupCommandHandler` calls `IRepository<TestGroupItem>.Delete(item)`** rather than the plan's `item.IsDeleted = true; _itemRepository.Update(item);` pattern used by every other soft-delete in the module. In this codebase the `SoftDeleteInterceptor` catches `EntityState.Deleted` and rewrites it to `Modified` + `IsDeleted = true`, so behavior is correct at run time — but the code is inconsistent with the rest of the module and the plan.

4. **`RenameTestGroupCommand` shape:** plan says `(int TestGroupId, string NewName)`. Code declares `(int Id, string GroupName)`. Cosmetic deviation.

5. **`UpdateTestInGroupCommand` shape:** plan says `(int TestGroupItemId, decimal Price, int? DisplayOrder)`. Code declares `(int Id, decimal Price, int? DisplayOrder = null)`. Cosmetic deviation; the handler correctly makes `DisplayOrder` optional.

6. **No `TestGroupDto.TotalPrice` sanity test for zero-item groups** in the handler tests — only the entity-level `TotalGroupPrice_ReturnsZeroForEmptyGroup` exists.

7. **`ManageTestGroupsCommand` scenario:** plan says leave it in place, mark it obsolete. Reality: the whole `Features/TestGroups/Commands/ManageTestGroups/` folder has been **removed**. That is a stricter cleanup than the plan asked for and could theoretically break Presentation callers, but Presentation is out-of-scope for the audit and this is arguably the cleaner end state.

### Slice 8 — Visit-side integration — Implemented with Deviations

**Evidence:**
- Domain: `Domain/Entities/Core/VisitTest.cs` — `SourceTestGroupId` (int?) and `TestGroupNameSnapshot` (string?) both present.
- EF: `Configurations/Core/VisitTestConfiguration.cs` — property mapped, `HasMaxLength(200)`, `HasIndex(e => e.SourceTestGroupId)`, no FK to `TestGroups` (correct per OQ-7).
- Migrations: `20260820111715_Slice8VisitTestGroupSnapshot.cs` + `20260820150952_Phase2B_VisitTestIndexAndNullable.cs`.

- Tests: `Slice8SelectionGroupPricingTests.cs` + `Slice8VisitTestGroupSnapshotIntegrationTests.cs`.

**Deviations:**

1. **`IVisitTestSnapshotter` interface not extended.** The plan specified a new overload:
   `CreateVisitTestSnapshot(Test test, int visitId, decimal price, bool isOutsourced, int? sourceTestGroupId, string? testGroupNameSnapshot)`
   Reality: the interface is unchanged; the handler assigns `visitTest.SourceTestGroupId = selectionGroup.Id` and `visitTest.TestGroupNameSnapshot = selectionGroup.GroupName` on the returned object AFTER calling the existing 4-arg overload. Runtime-equivalent but structurally different.

## 5. Dependency Impact Analysis

```
Slice 1 (read + mapping)  ──┬── Slice 2 (rename)                    [OK]
                            ├── Slice 3 (delete)                    [OK]
                            ├── Slice 4 (incremental item CRUD)     [OK, deviations local]
                            └── Slice 9 (print enrichment)          [NOT IMPLEMENTED]

Slice 5 (schema uplift) ──┬── Slice 6 (per-action triads)           [OK, no mapping profile]
                          │       └── Slice 7 (print query)         [OK shape but flat/no currency]
                          │       └── Slice 10 (integration)        [OK w/ file-split deviation]
                          └── Slice 8 (visit integration)           [OK, snapshotter unchanged]
                                  └── Slice 10 (integration)        [OK]
```

**Impact of deviations on downstream slices:**

1. **Slice 5 → Slice 6 → Slice 7:** Because Slice 6 chose not to create `TestGroupMappingProfile`, Slice 7's print DTO population is also hand-rolled inside its handler. A future addition of `TurnaroundTime` / `Categories` to `TestGroupPrintDto` will require modifying the handler again rather than a profile change. Increased maintenance cost, no runtime effect.

2. **Slice 5 → Slice 8:** The chosen non-extension of `IVisitTestSnapshotter` means any consumer that goes through `IVisitTestSnapshotter` directly (bypassing `AddTestsToVisitCommandHandler`) will silently produce `VisitTest` rows with null group snapshots. Only the one handler currently uses the snapshotter, so risk is contained but real.

3. **Slice 1 → Slice 9:** Slice 9 was supposed to consume the eager-load method added in Slice 1 (`GetByIdWithItemsAsync`). It DOES consume it, but its downstream DTO enrichment never happened, so the "print" path today is functionally equivalent to Slice 1's raw read minus the `Categories`/`Currency` upgrade.

4. **Slice 4 → Slice 10:** The missing filtered-index behaviour required a corrective `Phase1C_FixPriceListItemUniqueIndexFilter` migration. Integration tests are run against the final migrated state and therefore pass, but a rolling deployment from an intermediate revision could produce incorrect uniqueness behaviour until Phase1C is applied.

5. **Slice 8 → Slice 10:** Same story with `Phase2B_VisitTestIndexAndNullable` fixing Slice 8's `TestGroupNameSnapshot` NOT NULL bug.
