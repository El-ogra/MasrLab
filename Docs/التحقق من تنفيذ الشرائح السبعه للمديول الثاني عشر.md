- `src/MasrLab.Infrastructure/Persistence/Configurations/Settings/PriceListConfiguration.cs` — `IsLabToLab` required with default `false`, plus a filtered unique index `HasFilter("[IsLabToLab] = 1")`, mirroring the existing `IsDefault` technique.
- Migration **M1** exists: `20260820210933_Slice12_ReferralEntityLabToLabDiscriminator.cs` — adds `City`, `Commission`, `Discount` (nullable), `IsLabToLab` (non-nullable, default), the filtered unique index, and the FK. The model snapshot confirms all columns and the filtered index.

- Tests: 12 domain invariant tests (`ReferralEntitySlice12Tests.cs`) and 5 LocalDb schema tests (`Slice12_DomainSchemaIntegrationTests.cs`), including the "second Lab-to-Lab list rejected by unique index" case and the "multiple `false` allowed" case.

**Deviation (cosmetic, D-11):** The plan names the index `UX_PriceLists_IsLabToLab`; the migration creates it as `IX_PriceLists_IsLabToLab`. Functionally identical; severity: trivial.

### 4.2 Slice 2 — Correct & Complete the Add Pipeline

**Status: IMPLEMENTED WITH DEVIATIONS**

What conforms:
- `AddReferralEntityCommand` now carries `City`, `Discount`, `Commission`, and `int? PriceListId` (was `int`).
- `AddReferralEntityCommandValidator` uses per-type `When(...)` branches: `TreatingDoctor` → `PriceListId` must be null, `Discount`/`Commission ≥ 0` when present; `ReferralEntity` and `OutsourcedSamples` → `PriceListId > 0`.
- `AddReferralEntityCommandHandler` resolves the price list per type: `TreatingDoctor` → forced null; `OutsourcedSamples` → resolved server-side from `IPriceListRepository.GetLabToLabAsync()` (which was added to the interface and implemented in `PriceListRepository`), throwing `BusinessRuleViolationException` if none exists; `ReferralEntity` with null list → business error.
- `IPriceListRepository.GetLabToLabAsync` exists and is implemented (`FirstOrDefaultAsync(p => p.IsLabToLab)`).

Deviations:
- **D-01 (defect, medium):** The plan requires "Handler must reject a soft-deleted or nonexistent `PriceListId` (load via `IPriceListRepository`)". `AddReferralEntityCommandHandler.Handle` **never loads or verifies** the caller-supplied `PriceListId` for the `ReferralEntity` branch — a nonexistent or soft-deleted list id passes validation and is persisted (only the database FK would catch a nonexistent id; a soft-deleted list passes entirely). Note the Update handler *does* perform this check, so the two pipelines are inconsistent. Location: `AddReferralEntityCommandHandler.cs`, the `ReferralEntity` branch.
- **D-02 (design deviation, low):** For `OutsourcedSamples`, the validator demands `PriceListId > 0` while the handler **discards the supplied value** and overwrites it with the Lab-to-Lab list id. Per the plan's OQ-4 server-side-enforcement intent, the client should not be forced to supply a value that is ignored. The rule is enforced, but the contract is misleading.
- **D-03 (flagged deviation, low):** The plan's default was to **drop `AccountBalance` from the create contract** (clarification Q-2). The command still requires `decimal AccountBalance`. The plan explicitly flagged this as pending product decision, so this is an unresolved open item rather than a hard defect.

Tests: only 2 pre-existing Add tests remain in Application.Tests; the mandated validator matrix (physician+list → invalid; referral without list → invalid; sent-samples with non-LabToLab list → invalid) is **not present** (part of D-05).

### 4.3 Slice 3 — Read Side: List, Detail, External-Lab Candidate Pool

**Status: IMPLEMENTED WITH DEVIATIONS**

What conforms:
- `GetReferralEntitiesQuery` (+ handler) → `IReadOnlyList<ReferralEntityDto>` via `IReferralEntityRepository.GetAllWithPriceListAsync` (soft-deleted rows excluded by the global query filter; no `includeArchived` parameter — as specified).
- `GetReferralEntityByIdQuery` (+ handler) → `ReferralEntityDto?` via `GetByIdWithPriceListAsync`.
- `GetExternalLabCandidatesQuery` (+ handler) → union predicate implemented in `ReferralEntityRepository.GetExternalLabCandidatesAsync`: `EntityType == OutsourcedSamples || (PriceList != null && PriceList.IsLabToLab)` — exactly OQ-5 Option D.
- `ReferralEntityMappingProfile` created, mapping phone value objects to strings and projecting `PriceListName` / `IsLabToLabPriceList`.
- `IReferralEntityRepository` exists with the three specified methods; `ReferralEntityRepository` implements them; both are registered in `DependencyInjection.cs` (line 91).

Deviations:
- **D-05 (test gap, medium):** No Application.Tests handler tests exist for any of the three queries (grep of the entire Application.Tests project shows zero references to `GetReferralEntities`, `GetReferralEntityById`, or `GetExternalLabCandidates`).
- **D-09 (test quality, medium):** The OQ-5 integration coverage in `Module12_ReferralParties_IntegrationTests.FullLifecycle_AllThreeEntityTypes_CRUD` **re-implements the union predicate as in-memory LINQ inside the test** instead of invoking `GetExternalLabCandidatesAsync` / `GetExternalLabCandidatesQueryHandler`. The production predicate is therefore never executed by any test; a regression in the repository method would go undetected.

### 4.4 Slice 4 — Edit Entity (OQ-2, OQ-3, OQ-7)

**Status: IMPLEMENTED WITH DEVIATIONS**

What conforms:
- `UpdateReferralEntityCommand` has **no `EntityType` member** (OQ-7 enforced structurally, compile-time).
- `UpdateReferralEntityCommandHandler` loads via the filtered repository (soft-deleted → `EntityNotFoundException`), never assigns `EntityType`, resolves the price list per type (doctor → null; sent-samples → re-locked to Lab-to-Lab, error if none; referral → existence check via `IPriceListRepository.GetByIdAsync` and error on null). It performs a plain field update with **no interaction with any visit/billing collaborator** — OQ-2 forward-only holds by construction.
- Command exposes the per-type editable field set (contact fields, `City`, `Address`, `Fax`, `Discount`, `Commission`, `PriceListId`).

Deviations:
- **D-04 (defect, medium):** The plan (§Slice 4.i) requires a "Validator matrix mirroring Slice 2's per-type rules". `UpdateReferralEntityCommandValidator` contains only `RuleFor(x => x.Id).GreaterThan(0)` and `RuleFor(x => x.Name).NotEmpty()`. There is no per-type validation — e.g., `Discount`/`Commission ≥ 0` is enforced on Add but **not on Update**, so an edit can persist negative values that creation would reject.
- **D-05 (test gap, medium):** The mandated handler tests — price-list swap with strict mock verification of zero billing interaction (OQ-2 regression guard) and the type-immutability contract assertion (OQ-7) — do not exist anywhere in Application.Tests.

### 4.5 Slice 5 — Delete Entity (OQ-1 Soft Delete)

**Status: FULLY IMPLEMENTED AS SPECIFIED**

Evidence:
- `DeleteReferralEntityCommand(int Id)` + handler + validator (`Id > 0`) all present.
- `DeleteReferralEntityCommandHandler` loads the entity, throws `EntityNotFoundException` when absent, throws `BusinessRuleViolationException("Entity is already deleted.")` on a second delete, sets `IsDeleted = true`, and saves — no hard delete, no reference-blocking, no cascade, exactly OQ-1 Option C.
- Post-delete behavior is verified by `Module12_ReferralParties_IntegrationTests.FullLifecycle_AllThreeEntityTypes_CRUD`: after delete, the default query returns 2 rows while `IgnoreQueryFilters()` returns 3 — the canonical OQ-1 archival assertion.
- The plan's Application-level "delete nonexistent id" test is absent (minor test-gap folded into D-05), but the handler behavior is simple and is covered in substance by the integration suite; this does not rise to a deviation of the slice's deliverable.

### 4.6 Slice 6 — Function 5 Uplift: Typed External-Lab Reference + OQ-6 Validation

**Status: IMPLEMENTED WITH DEVIATIONS**

What conforms:
- `src/MasrLab.Domain/Entities/Core/Test.cs` — `int? OutsourcedLabReferralEntityId` + navigation `ReferralEntity? OutsourcedLabReferralEntity`; legacy `OutsourcedLabName` retained.
- `TestConfiguration` maps the FK with `DeleteBehavior.Restrict` and an index; migration **M2** `20260820215643_Slice6_TestTypedExternalLabRef.cs` adds the column, index, and `FK_Tests_ReferralEntities_OutsourcedLabReferralEntityId` (Restrict). Snapshot confirms.
- `AddTestCommand` / `UpdateTestCommand` carry `OutsourcedLabReferralEntityId`; both handlers null it out when `SentOutsideLab == false` ("nulled/ignored" per plan).
- Both validators implement OQ-6: `When(SentOutsideLab)` → lab id `NotNull().GreaterThan(0)`, `OutsourcedCostPrice NotNull().GreaterThanOrEqualTo(0)` (**zero allowed**); `When(!SentOutsideLab)` → both must be null. **No** `PatientPrice ≥ CostPrice` rule exists — OQ-6's "no relational constraint" is honored.

Deviations:
- **D-06 (defect, high):** The plan requires the external lab to be "a member of the OQ-5 candidate pool (handler-level check …)". Neither `AddTestCommandHandler` nor `UpdateTestCommandHandler` takes any referral-entity repository or performs any pool-membership (or even existence) check — a `TreatingDoctor` id, or any arbitrary integer, is accepted at the application layer and only the raw FK would fire at the database. The plan's required handler test ("lab id outside the OQ-5 pool → business-rule rejection") is correspondingly absent.
- **D-07 (defect, medium):** The plan explicitly requires `TestDto` and `TestWithReferencesDto` to "expose `OutsourcedLabReferralEntityId` (+ resolved lab name)" and the two query handlers to project it. **Neither DTO contains the property** and neither `GetTestWithReferencesQueryHandler` nor `GetTestsListQueryHandler` projects it — the typed reference is write-only through the API surface at this commit.
- **D-08 (spec conflict, low–medium):** OQ-6 states both prices are "required, ≥ 0 (**zero allowed**)". Both validators carry the pre-existing `RuleFor(x => x.Price).GreaterThan(0)` (strictly positive), so a patient price of exactly 0 is rejected even when `SentOutsideLab` is true. The plan said to "assert explicitly" the ≥ 0 rule; the stricter legacy rule was left in place without resolution.

### 4.7 Slice 7 — End-to-End Integration & Regression Gate

**Status: IMPLEMENTED WITH DEVIATIONS**

What conforms:
- `tests/MasrLab.Infrastructure.Tests/Module12_ReferralParties_IntegrationTests.cs` exists with: full lifecycle over all three entity types (create → list → price-list swap edit → OQ-5 re-evaluation → soft delete → archival verification), typed-lab FK round-trip, and Lab-to-Lab unique-index rejection.
- The existing Add tests were updated consistently with the new contract (the two remaining referral tests reference the new behavior; no test still asserts the old unconditional `PriceListId > 0` rule).

Deviations:
- **D-09 (test quality, medium):** The suite drives `MasrLabDbContext` directly (entity constructors + `SaveChangesAsync`) rather than the CQRS commands/handlers the plan's lifecycle describes ("create Lab-to-Lab price list (Module 11 commands) → create all three entity types → …"). The plan's explicit step "verify historical snapshot unaffected" (a `VisitTest` snapshot assertion) is **not performed anywhere**. The OQ-5 pool is evaluated by re-implemented LINQ rather than the production query (see §4.3).
- **D-10 (gate unmet, high for sign-off):** The plan's completion criterion is "100% pass" of the full suite (new + pre-existing, including Module 11 integration tests). No test-run output exists in the repository at this commit, and the suite cannot be executed in the audit environment (no .NET SDK; LocalDb requires Windows/SQL Server). **The regression gate is therefore unverified — Module 12 cannot be certified green on the evidence available.**

## 5. Dependency Impact Analysis

Dependency chain (per the plan): **Slice 1 → Slice 2 → {Slice 3, Slice 4} → Slice 5 → Slice 6 → Slice 7**, with Slice 3's OQ-5 pool feeding Slice 6's lab validation.

```
Slice 1 (schema/entities)  ──► Slice 2 (Add pipeline) ──► Slice 3 (reads + OQ-5 pool)
        │                            │                          │
        │                            └──► Slice 4 (Edit)        │ (pool consumed by)
        │                            └──► Slice 5 (Delete)      ▼
        │                                                   Slice 6 (Function 5 uplift)
        │                                                            │
        └────────────────────────────────────────────────────► Slice 7 (E2E gate)
```

Assessed downstream impact:

- **Slice 1 → all later slices:** Slice 1 is fully implemented (cosmetic index-name deviation only). **No downstream impact.** All dependent slices build on a conformant foundation.
- **Slice 2 → Slice 4:** D-01 (missing price-list existence check) was **not propagated** — the Update handler performs the check the Add handler omits, leaving an asymmetric pipeline where invalid data can enter at creation but not at edit. D-02's discarded-value contract is mirrored in Update (same server-side override), so the quirk is at least consistent.
- **Slice 2/3 → Slice 6:** D-06 is the most consequential cross-slice effect: because Slice 6's handlers never consult the OQ-5 pool produced by Slice 3, the entire "validated external lab" promise of Function 5 degrades to an unchecked integer FK. A `TreatingDoctor` created in Slice 2 (with no price list) can be referenced as a receiving laboratory.
- **Slice 6 → consumers:** D-07 (field absent from DTOs/projections) means downstream screens/reports cannot display which registered lab a test routes to — only the legacy free-text name is readable.
- **Slices 2–6 → Slice 7:** Because the E2E suite bypasses the CQRS pipeline (D-09) and no full-suite run is evidenced (D-10), **none of the application-layer defects above (D-01, D-04, D-06, D-07, D-08) is capable of being caught by the current test suite** — the regression gate does not gate the layer where the defects live.

## 8. Closing Statement

**Verdict: Module 12 is NOT yet genuinely complete at commit `e32328aeaa5e0a384cea40baeb1788aab4fc23e1`.**

The structural implementation is real and substantial: every slice's code artifacts exist, both mandated migrations (M1, M2) are present and match the model snapshot, the OQ-1/OQ-4/OQ-5/OQ-7 decisions are correctly embodied in the schema and pipelines, and 20 Module-12-specific automated tests (12 domain + 8 LocalDb integration) exist.

However, the module cannot be certified complete on this evidence for three reasons: (1) a high-severity enforcement gap — Function 5 accepts any integer as the receiving laboratory because the OQ-5 candidate-pool check is absent from both test handlers (D-06); (2) the application-layer test coverage the plan mandates as the module's completion gate is largely missing, and the integration suite bypasses the very pipeline it should certify (D-05, D-09); and (3) the full-suite green run — the plan's explicit definition of done — is unevidenced at this commit (D-10).

With the 10 work items in §7 completed (none requiring schema change), Module 12 would satisfy the plan's definition of done.
