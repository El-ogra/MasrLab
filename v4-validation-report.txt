# 6. Validation of Feature Completeness

v4 covers the intended feature areas, but does not safely complete them because:

- multi-component saving is not concretely atomic;
- post-print correction fails for partial prints;
- print acknowledgement lacks the selection/visit context needed by its stated decorator;
- unentered/Pending items are not prevented from being printed/stamped;
- sidebar date filtering is incompatible with UTC VisitDate storage;
- reference values remain technically creatable at whole-test level.

# 7. Domain/Application/Infrastructure Validation

The current architecture can accommodate the proposed entities and commands. The synchronous edit-history insert can be atomic if it uses the same tracked DbContext and one SaveChanges call.

But v4 does not fully specify:

- immutable pre-edit snapshots for history construction;
- an event shape satisfying the binding audit-event decision;
- batch result entry;
- a durable reprint-required state;
- visit status reconciliation when tests are added after completion/printing.

# 15. Gaps Requiring Owner Decisions

## Gap G1 — Preview abstraction is incompatible with current reporting contracts

### What is missing, wrong, or blocking

v4 requires the preview to compose the same \`IDocument\` used for printing, but the current report contracts expose only rendered PDF bytes. v4’s \`_reportRegistry.Resolve(...).Compose(...)\` API does not exist.

### Repository evidence

- \`src/MasrLab.Infrastructure/Printing/IReportDefinition.cs:5-10\` exposes only \`Render(IPrintPayload)\`.
- \`src/MasrLab.Infrastructure/Printing/ReportDefinitionRegistry.cs:12-18\` exposes \`Get\`, not \`Resolve\`.
- \`src/MasrLab.Infrastructure/Printing/Reports/CombinedReport.cs:1-4\` directly renders PDF bytes.
- v4 §12.5 lines 520-526 depends on unavailable APIs.

### Why this blocks full achievement of the plan's two goals

Print Preview cannot be built as specified, so Q4 and Decision 12 cannot be delivered.

### Available options

#### Option A — Extend IReportDefinition to expose IDocument

- Description: add a composition method returning the QuestPDF document; PDF and XPS paths call that same method.
- Technical consequences: changes all report definitions and PrintService.
- Functional/business consequences: preserves preview/print fidelity.
- Effort/risk implications: moderate, controlled report-layer refactor.

#### Option B — Add a feature-specific report-composition factory

- Description: leave current IReportDefinition unchanged; create a separate factory used by both updated reports and preview.
- Technical consequences: introduces parallel composition ownership.
- Functional/business consequences: can satisfy Decision 12.
- Effort/risk implications: higher drift risk.

### Agent recommendation

Option A.

### Why this is the recommendation

It ensures PDF and XPS are generated from one report definition, exactly matching Decision 12’s fidelity intent.

### Exact question for the project owner

“Should v4 standardise all relevant report definitions on an \`IDocument\` composition contract so Preview and Print use the same document instance/model?”

### Status

Awaiting project owner decision
